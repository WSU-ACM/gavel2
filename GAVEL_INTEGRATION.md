# Gavel integration contract

This document specifies the changes required in
[`WSU-ACM/gavel2`](https://github.com/WSU-ACM/gavel2) to accept projects and
participants exported by this membership bot. It is an implementation contract
for the Gavel work; the membership bot does not yet produce these files.

The contract deliberately uses stable external identifiers. Gavel's current
project import generates database IDs and its participant import requires those
IDs, which makes a reliable two-system export impossible. Current imports are
also append-only, so replaying a file creates duplicate projects, participants,
login secrets, and invitation emails.

## Goals

- Import a complete project and participant roster without manually copying
  Gavel database IDs.
- Make an identical import safe to repeat.
- Update records that were imported previously instead of creating duplicates.
- Preserve Gavel's internal primary keys, participant login secrets, votes, and
  ranking state across repeated imports.
- Apply project and participant changes as one validated operation.
- Prevent roster changes from invalidating voting that has already started.
- Leave manually managed Gavel records outside this integration untouched.

## Non-goals

- Gavel does not match people by name or email.
- Gavel does not query Discord, MLH, or this bot's SQLite database.
- Gavel does not infer team membership from project names.
- This contract does not require support for multiple source events in one
  Gavel deployment.
- Existing headerless Gavel import formats do not need to become the integration
  format. They may remain as separate legacy/manual import paths.

## Import operation

Add an administrator-only "Membership roster import" operation that accepts
both of these UTF-8 CSV files in one request:

- `projects.csv`
- `participants.csv`

The operation MUST parse and validate both complete files before changing the
database. All database changes from both files MUST commit in one transaction.
If any row is invalid, nothing may be inserted, updated, or deactivated.

The UI may use two file inputs or one archive containing those exact filenames.
The transport choice is not part of the data contract. The operation must use
Gavel's existing administrator authentication and CSRF protections.

### `projects.csv`

The first row is a required header with these exact fields:

```csv
external_id,name,description,submission_url
```

Example:

```csv
15281-hacktoberfest:team:018f7f65,Project Alpha,A useful project,https://organize.mlh.io/participants/events/123/projects/456
```

Fields:

| Field | Requirements |
|---|---|
| `external_id` | Required, immutable, and unique within the file and Gavel. Treat as an opaque string. |
| `name` | Required project/team display name. It does not identify the record. Duplicate names should be rejected within an import to prevent operator confusion. |
| `description` | Required project description. |
| `submission_url` | Required absolute `http` or `https` OrganizerHQ URL. |

The integration does not supply location, tagline, video, or project website.
Gavel should either make those fields optional for integration-managed projects
or populate harmless internal defaults. Project details not represented here
remain available through `submission_url`.

### `participants.csv`

The first row is a required header with these exact fields:

```csv
external_id,name,email,description,project_external_id
```

Example:

```csv
15281-hacktoberfest:mlh:98765,Alice Example,alice@example.edu,Project Alpha member,15281-hacktoberfest:team:018f7f65
```

Fields:

| Field | Requirements |
|---|---|
| `external_id` | Required, immutable, and unique within the file and Gavel. This will identify an event-specific MLH registration. |
| `name` | Required participant display name from the active MLH registration. |
| `email` | Required email used for the Gavel invitation. Compare normalized values for duplicate detection, but retain the submitted value for display/delivery. |
| `description` | Required participant description; initially expected to identify the participant as a member of the named project. |
| `project_external_id` | Required external ID from a row in the accompanying `projects.csv`. |

Every exported participant is expected to have one project. Multiple
participants may reference the same project. A participant may reference only
one project.

## External identifiers

Both external IDs are generated by the membership bot and are opaque to Gavel.
Gavel MUST NOT parse them, derive display values from them, or assume that they
are numeric.

The exporter will namespace identifiers by MLH event so that IDs from different
events cannot collide. The expected conceptual forms are:

```text
<event>:team:<stable-team-id>
<event>:mlh:<registration-id>
```

The exact suffix format may change. Gavel should store at least 255 UTF-8
characters and compare the complete value exactly. Do not convert IDs to
integers or case-fold them.

## Persistence changes

Add nullable integration identity fields to the existing project/item and
participant/annotator models:

- `external_id`
- `managed_source`

For records imported through this contract, `managed_source` should have a
fixed value such as `membership_bot`. Existing and manually created records
must retain null integration fields.

Requirements:

- Add a unique constraint for non-null project `external_id` values.
- Add a unique constraint for non-null participant `external_id` values.
- Preserve all existing records during migration.
- Do not manufacture external IDs for existing records.
- Do not use project name or participant email as an integration key.
- Continue using Gavel's internal primary and foreign keys for relationships,
  votes, and ranking calculations.

If the deployed database cannot create a partial unique index, a normal unique
constraint on a nullable column is acceptable when that database permits
multiple null values.

## Import semantics

The two files represent the complete active roster managed by this integration.
Apply them as follows:

1. Resolve every row by `external_id` and `managed_source=membership_bot`.
2. Insert records that do not exist.
3. Update mutable fields on records that already exist.
4. Resolve participant projects through `project_external_id`, never through a
   Gavel database ID or project name.
5. Mark integration-managed participants absent from `participants.csv` as
   inactive.
6. Mark integration-managed projects absent from `projects.csv` as inactive,
   after participant changes have been evaluated.
7. Never deactivate, update, or delete records whose `managed_source` is null or
   belongs to another integration.

Deactivation rather than deletion is required so votes, auditability, and login
history are retained. If Gavel cannot safely deactivate a project that has
historical votes, it should retain the project and exclude it from new voting
instead of deleting it.

An existing external ID owned by a different `managed_source`, or used for the
wrong resource type, is a hard validation error.

An identical replay MUST produce no database changes other than optional import
audit metadata. In particular, it must not:

- allocate new internal IDs;
- rotate participant login secrets;
- reset voting priors or ranking state;
- clear votes;
- send another invitation email;
- change project membership.

## Mutable fields

Before voting starts, an import may update:

- project name, description, and submission URL;
- participant name, email, description, and project assignment;
- active state through presence or absence in the complete snapshot.

After any vote has been recorded, imports MUST reject changes that would:

- assign a participant to a different project;
- activate or deactivate a participant;
- activate or deactivate a project;
- introduce a new participant or project into the active event.

Metadata-only updates may remain allowed after voting starts if they do not
change voting eligibility or ownership. A no-op replay must remain allowed.
The rejection must occur during validation, before any part of the import is
committed.

This is stricter than only checking whether the affected participant has voted:
team membership also controls who may vote on a bracket match, so changing a
non-voter's project can still change election eligibility.

## Validation

At minimum, reject the entire import when:

- either file or required header is missing;
- headers are duplicated, unknown, or in the wrong file;
- a row has missing/extra cells or a required blank value;
- UTF-8 or CSV parsing fails;
- an `external_id` is duplicated;
- a project name is duplicated after trimming and case-folding;
- a participant email is invalid or duplicated after trimming and
  case-folding;
- `project_external_id` does not identify exactly one project in the same
  import;
- a URL is not absolute HTTP/HTTPS;
- a field exceeds its database limit;
- the import would violate the post-voting restrictions above.

Use a bounded upload size and row count. Blank rows should be rejected rather
than silently changing snapshot meaning. Trim insignificant surrounding
whitespace from names, email addresses, descriptions, IDs, and URLs before
validation; do not otherwise normalize external IDs.

The result page should report row numbers and safe reason codes. It may show the
submitted values back to the authenticated administrator, but application logs
and uncaught errors must not contain participant names, email addresses, IDs,
URLs, raw rows, or complete uploaded files.

## Invitations

Participant database changes and invitation delivery are separate concerns.

- Generate a login secret only when creating a genuinely new participant.
- Preserve the secret when updating, deactivating, or reactivating a
  participant.
- Send an automatic invitation only for a newly created active participant.
- Do not resend invitations during an unchanged replay.
- Do not rotate credentials when an email address changes.
- Perform email delivery only after the database transaction commits.
- Report invitation failures separately from import success so an operator does
  not replay the roster expecting the database transaction to roll back.
- Provide or retain an explicit administrator action for resending an
  invitation.

## Result reporting

After a successful import, report aggregate counts for:

- projects created, updated, unchanged, and deactivated;
- participants created, updated, unchanged, and deactivated;
- invitations sent and failed.

Do not call the whole import failed merely because a post-commit invitation
could not be delivered. Clearly state that the roster was saved.

Optionally store an import audit record containing the time, administrator,
file hashes, counts, and success/failure reason. Do not store raw CSV or
participant fields in that audit record.

## Existing Gavel behavior that must change

At the time this contract was written, Gavel's normal project importer accepts
headerless positional rows and creates a new `Item` for every row. Its
participant importer accepts a Gavel-generated project database ID and creates
a new `Annotator` and secret for every row. Neither path performs an upsert.

The integration path therefore must not call those insert loops unchanged. It
needs stable-ID lookup, cross-file project resolution, complete validation, and
transactional upsert/deactivation behavior as described above. Existing report
exports (`/api/items.csv` and `/api/annotators.csv`) are not suitable as import
formats and are outside this contract.

## Acceptance tests

The Gavel implementation is complete when automated tests demonstrate all of
the following:

1. A valid two-file import creates projects, participants, relationships, and
   one secret per participant.
2. Replaying the exact files changes no internal IDs, secrets, relationships,
   votes, ranking values, or active states and sends no invitations.
3. Changed metadata updates the same records rather than adding records.
4. A pre-voting participant project change updates the existing participant.
5. Missing integration-managed rows are deactivated while manual records are
   untouched.
6. Reintroducing a previously deactivated external ID reactivates the same
   internal record and preserves its secret.
7. Any malformed row or unresolved project rejects both files without partial
   changes.
8. Duplicate external IDs, project names, and participant emails are rejected.
9. A database failure rolls back changes from both files.
10. Once voting exists, eligibility, active-state, and project-assignment
    changes are rejected atomically, while a no-op replay succeeds.
11. Invitation failure does not roll back a committed roster and can be
    reported/retried without creating duplicate participants.
12. Existing rows from before the schema migration remain usable and are not
    altered by integration snapshot deactivation.
13. Only an authenticated administrator with valid CSRF state can perform the
    import.
14. Errors and application logs do not expose uploaded participant data.

## End-to-end handoff

Once both implementations exist, verify the contract with a disposable Gavel
deployment:

1. Create teams and assignments in the membership bot and lock the roster.
2. Generate both CSV files from one SQLite snapshot.
3. Import both files through the integration operation.
4. Confirm every participant owns the expected project and cannot vote on that
   project where Gavel applies ownership restrictions.
5. Replay the files and confirm there are no duplicate records or invitations.
6. Make a pre-voting correction, re-export, and confirm an in-place update.
7. Cast a test vote and confirm a subsequent roster-changing import is rejected
   without partial changes.
